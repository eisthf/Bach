# 원격 접속 — HTTP 프록시 경로에서 WebSocket이 끊기는 이유

GCP VM에서 실행 중인 Bach에 **개인 프록시(폰 USB RNDIS + 폰에서 띄운 HTTP 프록시)**
를 경유해 접속할 때 겪은 현상과 그 원인을 정리한 문서.

> **한 줄 결론**
> WebSocket은 **raw TCP 경로**에선 살고, **HTTP 프록시 경로**에선 죽는다.
> 그래서 폰 프록시를 거치는 `34.64.153.2:5173`은 무한 새로고침 루프에 빠지고,
> SSH 터널을 타는 `localhost:5173`은 정상 동작한다.

---

## 1. 환경

- Bach는 **GCP VM**에서 실행 (Vite dev 서버 포트 5173, 백엔드 8000).
- GCP 방화벽에서 **TCP 5173 인바운드는 열려 있음.** (단, §6처럼 SSH 터널만 쓸
  경우엔 5173·8000 인바운드는 **닫아도 된다** — 22만 있으면 충분하다.)
- 로컬 데스크탑은 인터넷 **직결 경로가 없음** — 유일한 통로가 **안드로이드 폰에서
  직접 띄운 개인 HTTP 프록시**(USB RNDIS, 예: `proxy.py`, `10.62.57.79:8080`)뿐이다.
- 직결 라우팅(NAT) 없이 이 프록시만이 유일한 통로이므로, 22 직결은 애초에 갈 길이
  없어 실패한다. SSH도 반드시 이 프록시를 경유해야 한다(`~/.ssh/config`의
  `ProxyCommand`).

---

## 2. 관찰된 현상 (A/B 대조)

| 친 URL | 실제 경로 | WebSocket | 결과 |
|---|---|---|---|
| `34.64.153.2:5173` | 브라우저 → **폰 프록시** → GCP | ❌ 죽음 | 페이지는 뜨나 **무한 새로고침 루프** |
| `localhost:5173` (SSH 터널) | 브라우저 → localhost → **ssh raw TCP** → GCP | ✅ 삶 | **정상** |

- 같은 GCP·같은 앱인데 **유일한 차이는 "폰 프록시 경유 vs ssh raw TCP"** 뿐이다.
- 인터넷 직결 환경(예: 집)에서는 `34.64.153.2:5173` 직접 접속도 멀쩡했다 →
  **GCP·Vite 설정 탓이 아님**이 배제된다.
- 따라서 루프의 원인은 **WebSocket이 HTTP 프록시 경로를 못 넘는 것**으로 확정된다.

---

## 3. 왜 WebSocket이 HTTP 프록시를 통과하지 못하나

WebSocket이 폰 프록시(HTTP 프록시) 경로를 통과하지 못하고 끊어지는 이유는, HTTP
프록시가 웹소켓의 독특한 **'연결 격상(Upgrade) 프로토콜'** 을 제대로 처리하지
못하거나 의도적으로 차단하기 때문이다. 하위 메커니즘을 3가지 관점으로 나눈다.

### 1) HTTP 프록시의 '동문서답' (Upgrade 헤더 누락)

웹소켓은 완전히 새로운 프로토콜이 아니라, 처음에는 일반 HTTP 요청으로 시작해서
중간에 웹소켓으로 전환하는 방식을 취한다. 이를 **Handshake(악수)** 라고 한다.

- 브라우저는 프록시에게 `Upgrade: websocket`, `Connection: Upgrade` 헤더를 담아
  일반 HTTP 요청을 보낸다. ("이 연결을 웹소켓으로 업그레이드해줘!")
- 일반적인 표준 HTTP 프록시는 자신이 모르는 헤더거나, **홉-바이-홉(Hop-by-Hop)**
  헤더로 분류되는 Upgrade 관련 헤더를 GCP 서버로 전달하지 않고 중간에 **삭제**해
  버리는 경우가 많다.
- 결국 GCP 서버(Vite)는 일반 HTTP 요청만 받게 되므로 웹소켓 연결을 맺지 못하고,
  브라우저는 연결 실패로 판단하여 **HMR(Hot Module Replacement) 루프**를 돌며
  새로고침을 반복한다.

### 2) 프록시의 5173번 포트 CONNECT 거부 (보안 정책)

HTTP 프록시 환경에서 `ws://`(보안이 없는 웹소켓)는 프록시가 패킷 내부를 들여다보며
제어하려고 하지만, `wss://`(암호화된 웹소켓)나 비표준 포트 통신은 프록시에게
**"통로만 열어줘(HTTP `CONNECT` 메서드)"** 라고 요청해야 한다.

- **표준 포트:** 프록시 서버들은 대개 `443`(HTTPS) 포트에 대해서는 보안 상
  통과(CONNECT)시켜 준다.
- **비표준 포트:** 하지만 현재 Vite가 사용하는 포트는 `5173`이다. 많은 프록시
  구현(또는 그 기본 설정)은 보안 취약점 공격을 막기 위해 `80`, `443` 이외의
  **비표준 포트에 대한 CONNECT 요청을 원천 차단**하도록 되어 있다.
- GCP의 TCP 5173 방화벽을 열어두었더라도, 데스크탑 바로 앞단에 있는 폰 프록시
  장비가 `34.64.153.2:5173`으로의 **터널링 자체를 거부**하면 웹소켓은 한 걸음도
  나아가지 못한다.

### 3) 프록시의 웹소켓 '프로토콜 비호환' (Keep-Alive 미지원)

HTTP 프록시는 기본적으로 **"요청(Request)이 오면 응답(Response)을 주고 끝낸다"**
는 단발성 HTTP 패킷 중계에 최적화되어 있다.

- 반면 웹소켓은 한 번 연결되면 데이터가 없어도 연결을 끊지 않고 계속
  **유지(Persistent Connection)** 해야 한다.
- 프록시 장비가 웹소켓 프로토콜을 명확히 지원하지 않으면, 웹소켓이 연결된 후
  한동안 패킷이 오가지 않을 때 *"이 연결은 끝난 HTTP 요청이구나"* 하고 프록시가
  중간에서 **연결을 강제로 끊어** 버린다.
- 연결이 끊기니 Vite 브라우저 클라이언트는 서버가 죽은 줄 알고 다시 연결을
  시도하며 **무한 루프**에 빠진다.

> 위 셋 중 어느 것이 실제로 작동했는지는 패킷을 떠봐야 단정할 수 있다. 하지만
> 세 경우 모두 결론은 같다 — **평문 `ws://`를 포워드 HTTP 프록시로 넘기는 것
> 자체가 원래 불안정한 시나리오**다.

## 4. SSH 포트 포워딩(`-L`)의 동작 원리

```
-L [로컬바인드주소:]로컬포트:대상호스트:대상포트
        (생략가능)     ▲            ▲────────▲
                    내 PC에서      SSH 서버(GCP) 입장에서
                    여는 포트       연결할 목적지
```

`-L 5173:localhost:5173` 을 쪼개면:

| 부분 | 값 | 의미 | 누구 기준? |
|---|---|---|---|
| 왼쪽 포트 | `5173` | **내 PC(로컬)** 에서 ssh가 새로 여는 **수신 포트** | 내 데스크탑 |
| `localhost` | `localhost` | 연결할 **목적지 호스트** | **⚠️ SSH 서버(GCP) 입장** |
| 오른쪽 포트 | `5173` | 그 목적지의 **포트** | SSH 서버(GCP) |

- **가장 중요한 함정:** 오른쪽 `localhost`는 내 PC가 아니라 **GCP VM 자기 자신**을
  뜻한다. 즉 "GCP가 자기 `localhost:5173`(거기 Vite가 떠 있음)에 연결한다".
- `ssh -L`은 **시스템 전체 VPN/프록시가 아니다.** 그저 내 PC `localhost:5173`에
  듣는 소켓 하나를 만들어, 거기 들어온 것만 ssh 안으로 실어 나르는 포트 포워딩이다.
- 그래서 브라우저에 `34.64.153.2:5173`을 치면 그건 `localhost:5173`이 아니므로
  **터널을 타지 않고** 여전히 폰 프록시로 직행한다. **반드시 `localhost:5173`으로
  접속**해야 터널을 탄다.

```
내 PC 브라우저 → http://localhost:5173   (왼쪽 5173, ssh가 듣는 포트)
   ▼  [ ssh 암호화 터널 ]
GCP VM 이 자기 localhost:5173 에 연결   (오른쪽 localhost:5173)
   ▼
GCP의 Vite dev 서버
```

## 5. 💡 왜 `ssh -L`(`localhost:5173`)에서는 살았나

`gcp-rblue`를 통해 터널을 뚫었을 때 정상 작동한 이유. 이 차이를 이해하면 원인이
더욱 명확해진다.

- **`34.64.153.2:5173` 접속 시:** 프록시가 웹소켓 헤더를 건드리고, 비표준
  포트(5173) 검사를 수행하므로 실패한다.
- **`localhost:5173` 접속 시:** SSH 터널링을 사용할 때, 폰 프록시는 이게
  웹소켓인지 Vite 포트인지 **전혀 모른다.** 오직 `gcp-rblue`가 요청한
  **GCP 22번 포트(SSH 암호화 터널) 통로 하나만** 중계해 줄 뿐이다.
- 웹소켓 패킷과 5173 포트 정보 전체가 SSH라는 단단한 껍질 속에 꽁꽁
  **암호화(raw TCP)** 되어 통과하므로, 중간의 폰 프록시가 이를 간섭하거나 차단하지
  못하고 GCP 내부까지 안전하게 배달된다.

> SSH가 프록시에 요청하는 것은 `CONNECT <GCP>:22` 단 하나다. 프록시는 그 22번
> 통로만 불투명하게 열어줄 뿐, 그 안에서 무엇이 흐르는지(웹소켓·HTTP·5173 등)는
> 알 수 없다. 그래서 §3의 세 가지 간섭이 전부 무력화된다.

## 6. 실용 결론

폰 프록시(또는 WebSocket을 못 넘기는 HTTP 프록시) 뒤에서는:

1. SSH 터널을 띄운다. **반드시 `~/.ssh/config`의 Host 별칭**(ProxyCommand 포함)을
   쓴다 — IP를 직접 쓰면 ProxyCommand가 적용 안 돼 ssh 자체가 안 붙는다.
   ```bash
   ssh -L 5173:localhost:5173 -L 8000:localhost:8000 gcp-rblue
   ```
2. 브라우저엔 반드시 **`http://localhost:5173`** 로 접속한다.
   (`34.64.153.2:5173`은 터널을 안 타므로 쓰지 말 것.)

### 방화벽 — SSH 터널만 쓴다면 5173 인바운드는 닫아도 된다

SSH 터널 경로에서 브라우저가 실제로 닿는 길은 다음과 같다:

```
브라우저 → localhost:5173 → [ssh 터널, GCP 22번 포트] → GCP 내부에서 localhost:5173
```

- 외부에서 GCP로 들어오는 연결은 **22번(SSH) 하나뿐**이다.
- 오른쪽 `localhost:5173`은 **GCP가 자기 자신(내부)에서** 5173에 연결하는 것이라
  **GCP 내부 통신** — 인바운드 방화벽을 거치지 않는다.

| 접속 방식 | 필요한 GCP 인바운드 |
|---|---|
| `34.64.153.2:5173` 직접 | **5173 열려야 함** (게다가 프록시 뒤에선 WS가 깨짐) |
| SSH 터널 (`localhost:5173`) | **22만 열리면 됨 — 5173·8000은 닫아도 됨** |

**보안상 권장:** SSH 터널만 쓸 거라면 **5173(과 열었다면 8000) 인바운드는 닫는
편이 낫다.** dev 서버를 외부에 직접 노출하지 않게 되고, 접근은 SSH 인증을 통과한
사람만 가능해진다. 22번도 가능하면 출처 IP를 제한하면 더 안전하다.

> **요약:** 폰 프록시 장비가 ① 웹소켓 전환 헤더를 탈색시키거나 ② 5173이라는
> 비표준 포트의 지속적 연결을 거부하는 것이 기술적 원인이다. SSH 터널은 이 모든
> 것을 raw TCP로 감싸 단일 `CONNECT`(22)로 통과시키므로 정상 동작한다. 이때
> GCP에 필요한 인바운드는 **22번뿐**이고, 5173·8000은 닫아도 된다.
