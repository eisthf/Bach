# Bach 매매 전략 — 상한가 따라잡기 (ULC)

Bach의 자동매매가 **실제로 구현한** 전략을 정리한 문서. 구현은
[`backend/app/strategy/ulc.py`](../backend/app/strategy/ulc.py)이며, 코드가 진실원이다.

원 명세는 참조 프로젝트의 문서다(Bach는 그 부분집합을 구현한다 — [끝부분](#원-명세와의-차이) 참고):

- `~/work/kiwoom/doc/상한가 전략.md` — 전체 명세(파라미터·시나리오·CLI)
- `~/work/kiwoom/doc/상한가 전략 시각화.md` — 흐름도

## 개요

상한가로 마감한 종목은 다음 날에도 이어서 오르는 경향을 노린다.

- **X** = 전일 종가(상한가). ka10081 일봉의 직전 거래일 종가.
- **Z** = 당일 시가. 검증된 KRX 정규장 0B 체결 이벤트의 시가 필드에서 확보.

장 시작(09:00) 시점에 `MONITOR` 상태였던 종목만 `AUTO_TRADING`으로 진입하며
([상태머신](../README.md#상태머신)), 이때 종목마다 엔진이 셋업된다.
엔진은 틱마다 판단한다. 기본 주문은 시장가이며, 선택 시 1차 매수만 매도 3호가 지정가로 낸다.

X는 전일 종가 REST API, Z는 검증된 정규장 체결 이벤트의 시가를 사용한다.
시가 캐시는 한국 날짜별로 유효성을 확인한다. REST 일봉·분봉·시세표로 시가를
대체하지 않으며 차트 조회도 시가 캐시를 변경하지 않는다.
기준가가 없거나 조회가 실패하면 종목별로 **최대 60초 동안 3초 간격으로 준비를 재확인**한다.
시가는 메모리만 확인하고, 전일 종가 REST는 성공하면 당일 캐시를 사용한다.
조회 소요 시간도 제한 시간에 포함한다. 준비 중에는 기준가 확인 대기 안내를
표시하고 주문하지 않는다. 확보되면 엔진을 시작하고, 시간 초과 시 수동매매로
인계한다(⚠️ 로그). 수동 전환·종목 삭제·장 종료·리셋 시 대기를 취소한다.
다른 종목의 준비와 장 시계는 대기에 막히지 않는다. 틀린 X는 진입 필터·시나리오 분류·2차 매수가·상한가
매도선을 하루 종일 조용히 오염시키기 때문이다. 한 종목의 셋업 실패가 다른
종목의 장 시작 처리를 막지 않도록 종목별로 격리돼 있다.

## 흐름

```
[셋업: X, Z 확보]
   │
   ├─ X < 1,000원        ────────────→ ❌ SKIP (저가주)
   ├─ Z ≥ X×(1+w)        ────────────→ ❌ SKIP (갭 과도)
   ├─ Z < X 이고 allow_lower_open=false → ❌ SKIP (하락 시가)
   │
   ▼ [시나리오 분류]              (p=0.05, p1=0.07 기본)
   ├─ SC1:      Z < X×(1+p)   → 2분할: [Z, X×(1−q)]
   ├─ SC2: X×(1+p) ≤ Z < X×(1+p1) → 2분할: [Z, X]
   └─ SC3: X×(1+p1) ≤ Z       → 3분할: [Z, Z×0.95, Z×0.9025]
   │
   ▼ [분할매수 ACCUMULATING]
   │   · 진입 전 지연 가드: 현재가 ≥ X×(1+w) → ❌ SKIP
   │     (셋업이 밀려 그 사이 갭 상한을 넘었으면 진입하지 않음)
   │   · 1차는 첫 틱에 즉시, 이후 차수는 현재가 ≤ 목표가 도달 시
   │   · 한 틱에 한 차수만 실행
   │   · 매수 주문 실패한 차수는 재시도하지 않음(무한루프 방지)
   │   · ulc_first_buy_only=true 면 1차만 실행
   │   · 전 차수 완료 → HOLDING
   │
   ▼ [청산] — 익절은 1차 매수 직후부터, 분할 미완료(ACCUMULATING) 중에도 평가
   ├─ 손절: 현재가 ≤ 평단×(1−sl)
   │        ├─ manual_on_stop=false → 전량 매도
   │        └─ manual_on_stop=true  → 자동매도 없이 수동매매 인계
   │        (분할매수 전 차수 체결 이후에만 활성 — 익절과 달리 게이트 있음)
   ├─ 익절: 현재가 ≥ 평단×(1+tp)   (발동 시 미체결 분할 leg 는 소멸)
   │        ├─ trailing=false → 전량 매도
   │        └─ trailing=true  → 절반 매도 후 TRAILING 진입
   │
   ▼ [TRAILING] (trail_max = 이후 최고가 추적, 판정 우선순위 순)
   │   ① 손절:       현재가 ≤ 평단×(1−sl)      → 잔량 청산
   │   ② 상한가 도달: 현재가 ≥ X×1.295          → 잔량 청산
   │   ③ 보장 익절:   현재가 ≥ 평단×(1+g)       → 잔량 청산
   │   ④ 트레일링 스탑: 현재가 ≤ trail_max×(1−t) → 잔량 청산
   │
   ▼ [DONE] → 계좌 잔량 확인 → POSITION-FLAT → MANUAL_TRADING 복귀
```

**매도 주문이 전송 실패하면** 상태를 바꾸지 않고 다음 틱에 자연 재시도한다
(청산 조건은 다음 틱에도 대개 참이다). 전송 실패는 주문번호를 받지 못한
경우라 재시도해도 중복 주문이 아니다. 주문은 나갔으나 체결되지 않은 경우는
이 경로가 아니라 아래의 계좌 잔량 확인이 담당한다.

청산은 버튼이 아니라 매매의 *결과*다. 엔진이 전량 매도해 보유가 0이 되면
`POSITION-FLAT` 이벤트로 `MANUAL_TRADING`에 복귀한다. 이때 Hub가 **계좌
잔량을 재확인**해서, 부분체결 등으로 잔량이 남아 있으면 '청산 완료' 대신
경고를 남기고 수동매매로 인계한다(자동 재매도는 하지 않는다 — 기존 매도가
미체결 상태일 수 있어 중복 매도 위험).

## 파라미터

1차는 첫 판단 시점의 시장가 주문이다. 옵션을 켜면 주문 직전 조회한 매도 3호가로
지정가 매수를 낸다. 로그의 당일 시가는 시나리오 분류의 참고값이다.
2차 이후 조건가는 일반 주식의 KRX 호가 단위로
내림한다(예: 30,550×0.95=29,022.5 → 29,000원). 원래의 `현재가 ≤ 계산값`
조건을 보존하며, 주문은 여전히 시장가다. 호가 단위는
[KRX 일반 주식 규정](https://regulation.krx.co.kr/contents/RGL/03/03020100/RGL03020100.jsp)을 따른다.

[`AutoConfig`](../backend/app/models.py) — UI의 '자동매매 설정'에서 종목별로 조정.

| 파라미터 | 기본값 | 의미 |
|---|---|---|
| `max_buy_amount` | 500,000원 | 총 투자액. 분할 차수에 배분 |
| `ulc_p` | 0.05 | SC1/SC2 경계 갭 비율 |
| `ulc_p1` | 0.07 | SC2/SC3 경계 갭 비율 |
| `ulc_q` | 0.05 | SC1 2차 매수가: X×(1−q) |
| `ulc_w` | 0.15 | 진입 갭 상한(Z ≥ X×(1+w)면 SKIP) |
| `ulc_allow_lower_open` | false | 하락 시가(Z<X)도 진입 허용 |
| `ulc_first_buy_ask3` | false | 1차 매수를 현재 매도 3호가 지정가로 주문. 호가 조회 실패 시 시장가 대체 없음 |
| `ulc_tp` | 0.05 | 익절 비율(평단 대비) |
| `ulc_sl` | 0.05 | 손절 비율(평단 대비) |
| `ulc_manual_on_stop` | false | true면 분할 완료 후 손절선 도달 시 자동매도 없이 수동 인계 |
| `ulc_trailing` | false | 익절 시 절반 매도 후 트레일링 |
| `ulc_t` | 0.02 | 트레일링 스탑: trail_max 대비 하락률 |
| `ulc_g` | 0.15 | 트레일링 중 보장 익절 비율 |
| `ulc_first_buy_only` | false | 1차 매수만 실행 |
| `use_3min_bar_timing` | false | true면 완성된 3분봉의 종가 확정 시에만 매매 조건 평가 |

`use_3min_bar_timing`을 활성화하면 봉 안에서 조건가를 일시적으로 통과해도
주문하지 않는다. 다음 3분 구간의 첫 틱이 들어와 직전 봉 종가가 확정될 때
한 번만 판단한다. 기본 주문은 확정 직후의 시장가로 실행되므로 판단 종가와 실제
체결가는 다를 수 있다.

## 평단·수량의 진실원 (실거래)

주문 REST(kt10000/kt10001) 응답에는 체결가가 없다(주문번호만). 그래서 평단은
세 경로로 확정되며, 익절·손절 판단의 기준이 된다:

| 순서 | 경로 | 시점 | 성격 |
|---|---|---|---|
| 1 | 주문 시 직전 틱 가격 | 즉시 | 추정치(임시). mock에서는 즉시 체결이라 정확 |
| 2 | **00 주문체결 이벤트** (단위체결가 FID 914) | 체결 즉시 | 1차 진실원. 이 엔진의 주문만 누적 |
| 3 | 계좌 kt00018 폴링 | ~2초 | 안전망. 이벤트 유실·재시작 대비 |

계좌 기준 보정 규칙(보수적):

- 계좌 수량이 추정보다 **적으면** 실보유에 맞춘다(과다 매도 방지).
- **많으면** 건드리지 않는다 — 자동매매 이전부터 있던 보유분을 엔진이 팔지 않게.
- 수량이 정확히 일치할 때만 계좌 평단을 채택한다(실체결 평단이 있으면 그쪽 우선).
- 계좌가 0을 보고하면 무시한다(주문 직후 체결 미반영일 수 있음).
- 평단이 확정되기 전에는 익절·손절 판단 직전에 매 틱 재보정한다.
- 청산 수량은 항상 실보유 기준이다.

검증은 [`backend/tests/`](../backend/tests)의 회귀 테스트가 담당한다.

## 원 명세와의 차이

kiwoom 문서의 전체 명세 중 Bach가 구현하지 않은 것:

- **다일 보유·D+5 강제청산 없음** — Bach는 당일 완결형. 장 종료 시 엔진을
  정리하고 전 종목 `MANUAL_TRADING` 복귀.
- **분할 매수가 수동 지정(`y_sc1`/`y_sc2`/`y1_sc3`/`y2_sc3`) 미지원** —
  항상 공식값 사용.
- **틱 전용 추가 옵션 없음** — `use_tick_buy`,
  `tick_instant_profit_percent`는 필드조차 없음.
- **ETF/ETN 전용 호가 단위 미지원** — 추가 매수 조건가는 일반 주식 기준으로 보정.


## 서버 재시작과 수동 인계

서버는 종목·설정·매매 상태와 재시작 인계 사유를 계좌별로 저장한다.
엔진의 분할매수 단계, 트레일링 최고가, 주문 이력은 복원하지 않으므로
저장된 AUTO_TRADING 및 MONITOR는 자동 재개하지 않고 MANUAL_TRADING으로 인계한다.
장중에는 수동 상태에서 자동매매로 다시 진입할 수 없다. 장전 또는 장 종료 후에는 사용자가
보유 종목과 미체결을 확인한 뒤 PUSH로 다시 감시 등록하면 인계 표시가 해제된다.

시작 시 계좌 잔고도 조회하여 저장 목록에 없는 보유 종목까지 수동매매로 추가한다.
저장된 자동/감시 상태 또는 잔량이 있으면 자동매매 보호가 없다는 안내를
상태 응답, 서버 로그, 웹소켓 로그와 종목 카드에 남긴다. 이 안내는 재접속과
재시작에도 유지되며 숨김·컴팩트 상태에서도 보인다. 주문·취소·자동 청산은 하지 않는다.
잔고 조회 실패는 빈 계좌로 간주하지 않고 계좌 경고를 표시한다.
조회하지 못한 종목 목록은 직접 계좌에서 확인해야 한다.

## 인증 복구 중 주문 처리

계좌별 토큰을 만료 전에 갱신하고, 인증 거부를 받은 **조회**는 갱신 후 한 번 재시도한다.
실시간 재로그인 후에는 잔고·초기 시세를 다시 조회한다. 이 재동기화 자체는 주문을 생성하지 않는다.
주문 POST는 통신 오류·HTTP 429·인증 거부를 이유로 전송 계층에서 자동 재전송하지 않는다.
전략의 기존 다음 틱 판단·실패 처리와는 별개이며, 불명확한 주문 결과의 접수 확인을 대체하지 않는다.

### 첫 매수 전 KRX 시가 검증

틱 판단 모드에서는 엔진 준비 직후 최신 틱을 한 번 평가한다. 준비 중에 이미
소비된 시가 틱 때문에 다음 체결까지 진입이 멈추는 상황을 방지한다.
재사용 대상은 당일 09:00 이후 수신한 검증된 정규장 틱으로, 수신 후 3초
이내여야 한다. 조건에 맞는 틱이 없으면 새 틱을 기다리며 `auto_startup_tick`
로그에 평가 여부와 틱 경과 시간을 남긴다. 3분봉 모드는 기존 봉 확정 시점을 따른다.
준비 직후 평가와 실시간 평가를 종목별 잠금으로 직렬화하고, 재사용한 틱과
그 이전 대기열 틱은 다시 평가하지 않는다. 주문은 기준가 준비 재시도·시간제한
범위 밖에서 실행한다.

키움 계좌는 전일 종가 X만 REST로 조회하고, 당일 시가 Z는 검증된 KRX
실시간 주식체결(0B) 이벤트의 `16` 필드에서 얻는다. day_open은 당일 이벤트
캐시만 읽으며 REST를 호출하지 않는다. 차트 조회는 이 캐시를 변경하지 않는다.
기준가 준비 재시도 중에도 시가는 메모리만 확인하며, REST 전일 종가는 성공하면
당일 캐시를 사용한다. 이벤트가 먼저 오면 시가를 보관하고 전일 종가 조회가
완료된 뒤 사용한다. 두 값이 모두 있어야 매수 계획을 만든다. 이벤트가 오지
않으면 기존 준비 제한 시간 후 수동 인계한다. 일봉·분봉으로 시가를 대체하지 않는다.
`20` 체결시간이 정규장 범위이며 수신 시각보다 미래가 아니고, `290=2`(장중),
`9081=KRX`, `15` 체결량의 절댓값이 양수, `16` 시가가 양수인 메시지만 검증한다.
필드가 없으면 검증하지 않는다. 현재가를 시가로 대체하지 않으며 시가가 전일
종가와 같다는 이유로 거부하지 않는다.

첫 주문 전 검증된 시가가 준비 단계의 시가와 다르면 진입 필터, 시나리오,
분할 금액과 목표가를 다시 계산하고 `auto_open_revalidated` 이벤트에 두 시가,
출처와 틱 시각을 기록한다. 이미 매수 단계가 진행된 엔진은 계획을 변경하지
않는다. 기존 기준가 준비 제한 시간과 손절 정책은 유지한다.

근거: `kiwoom_rest_api_full_v4.md` 및 `kiwoom-rest-api-spec.json`의
ka10081(일자·거래량·시가), 0B(체결시간·체결량·장구분·거래소구분·시가).
이 검증은 과거 API 원본 응답의 오류를 입증하는 것이 아니라 잘못된 시가
후보가 첫 주문의 분할 계획에 그대로 사용되는 것을 방지한다.

### 자동매수 구간별 지연 계측

`backend/logs/events.log`의 `auto_setup_timing`, `auto_buy_timing` 이벤트를
계좌·종목·주문번호로 조회한다. `trace_id`는 주문 시도마다 달라 실패한 시도도
구별한다. 모든 소요 시간은 프로세스의 단조 시계로 계산한 밀리초이며,
로그 행의 UTC timestamp는 기록 요청 시각이다. 파일이 실제로 쓰인 시각과는 다르다.

| 필드 | 측정 구간 |
|---|---|
| prev_close_lookup_ms | 준비가 성공한 회차의 전일 종가 조회 호출(캐시·스레드 대기 포함) |
| open_to_setup_ms | 당일 첫 검증된 시가 메시지 수신 → 시나리오 준비 완료 |
| setup_to_decision_ms | 준비 완료 → 해당 매수 판단 |
| tick_to_decision_ms | 판단에 사용한 틱 수신 → 매수 판단 |
| decision_to_worker_ms | 매수 판단 → 주문 스레드 실행 시작 |
| worker_to_gate_ms | 주문 스레드 시작 → REST 호출 간격 제한 대기 시작(인증 등 포함) |
| rest_gate_wait_ms | REST 슬롯 대기 |
| http_response_ms | requests.post 호출 직전 → 반환 또는 예외 |
| decision_to_return_ms | 매수 판단 → 주문 작업 반환 |
| open_to_http_ms | 첫 검증된 시가 수신 → HTTP 호출 직전 |
| tick_to_http_ms | 판단 틱 수신 → HTTP 호출 직전 |

수신 시각은 WebSocket 프레임을 애플리케이션이 받은 시각이며 거래소에서
체결된 시각이 아니다. 3분봉 모드의 틱 시간은 판단에 사용한 직전 봉의 마지막
틱을 기준으로 하므로 봉 확정 대기도 포함된다. 데이터가 없는 구간은 필드를
생략한다. 주문 응답은 실제 체결이 아니며 실제 체결까지의 지연은 측정하지 않는다.
취소 시 `error_type=CancelledError`는 대기 취소를 의미한다. 스레드의 HTTP 요청은
계속 진행할 수 있으므로 이 행을 주문 미전송/실패 확정으로 해석하지 않는다.

매매 경로에서는 시각을 메모리에 보관하고 주문 작업 반환 후 계측 행을 큐에
넣는다. 기존 이벤트 로그도 전용 스레드에서 JSON 변환·파일 쓰기·회전을 수행한다.
큐 한도는 8192개이며 포화 시 새 로그를 버리고 누락 수를 누적한다. 이후 로그의
`log_dropped_total`, `log_write_errors_total` 및 `/api/health`의 `event_log`로
상태를 확인할 수 있다. 종료 시 최대 2초간 쓰기 스레드를 기다린다. 강제 종료나
장시간 디스크 장애에서는 메모리에 남은 로그가 유실될 수 있다.

메모리 큐·시계 호출·스레드 CPU 사용의 비용까지 0으로 만드는 것은 아니다.
기존 상태 저장 파일 I/O와 기타 콘솔 로깅은 별도 경로이므로 총 매매 지연을
이 계측 로그만으로 모두 설명할 수는 없다. 인증정보와 HTTP 본문은 기록하지 않는다.
