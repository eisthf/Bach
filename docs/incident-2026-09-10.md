# 2026-09-10 오전 조회 장애 분석

분석 대상: 사용자가 제공한 07:50 상한가 조회 실패, 08:01 성공, 08:06 잔고 실패 화면.
시간은 별도 표시가 없으면 한국 시각(KST). 조회 대상일은 2026-09-09이다.
분석 기준 소스: `1c1df2c`. 운영 코드 수정·서버 재시작·실계좌 API 호출 없이 조사했다.

## 결론

두 원인이 독립적으로 존재한다.

1. **07:50 → 08:01:** KRX의 전일 데이터 제공 시각이 다음 영업일 08:00이다.
   07:50에는 아직 없는 데이터를 요청했고, 08:01에는 게시된 데이터를 조회했다.
   앱은 정상적인 게시 대기를 휴장일과 같은 예외로 처리해 `조회 실패`라고 표시한다.
2. **잔고·시세 장애:** 키움이 접근토큰을 무효로 판정했다. 서버 터미널에 잔고,
   분봉, WebSocket 모두 `8005:Token이 유효하지 않습니다`가 남아 있다.
   토큰을 최초 한 번만 발급하고 갱신하지 않는 구현 때문에 자동 복구되지 않는다.

키움 토큰의 **무효 상태와 갱신 부재는 확인됐다.** 무효화의 직접 계기가 유효기간
만료인지 별도 폐기인지는 최초 발급의 실제 `expires_dt`가 남아 있지 않아 구분할 수 없다.
동일 서버가 전전날부터 계속 실행된 점에서 만료가 유력하다.

## 첫 번째·두 번째 화면: KRX 게시 시각

KRX 공식 FAQ의 「특정 일자의 경우, 데이터를 조회해도 호출이 안됩니다. 이유가
무엇일까요?」는 당일 조회 또는 익일 08:00 이전에는 데이터가 조회되지 않으며,
영업일 기준 익일 08:00에 갱신한다고 안내한다.

- [공식 FAQ](https://openapi.krx.co.kr/contents/OPP/COMM/faq/OPPCOMM004.cmd)
- 페이지가 사용하는 공개 목록 API: `OPPCOMM004D1.cmd`에
  `pageNum=1&rowCount=10&totalCount=0&pageCount=10`을 전달해 본문을 직접 확인했다.

코드의 처리 순서는 다음과 같다.

1. `main.py:303` 이후 라우팅에서 9월 10일에 지정한 9월 9일은 과거 일별 조회로 간다.
2. `krx_api.py:_fetch_market()`이 `basDd=20260909`로 코스피·코스닥을 요청한다.
3. `screener.py:227`에서 지정일 시세가 비어 있으면 `NotATradingDay`를 발생시킨다.
4. `main.py`는 이를 HTTP 404로 변환한다. 오류 문구는 첫 화면과 정확히 일치한다.
5. 게시 후에는 9월 9일과 9월 8일 종가를 비교해 결과를 만든다.

두 번째 화면의 `종가 기준`, `직전 거래일 2026-09-08`, `6종목 / 2,765종목`은
이 경로와 일치한다. 이는 9월 10일 장전의 실시간 상한가 목록이 아니다.
KRX 인증은 키움 인증과 별개이므로 이 성공이 키움 잔고 복구를 의미하지 않는다.

추가로 `krx_api.py:46,223,230`은 빈 결과를 300초 캐시한다. 07:50 조회의 캐시는
08:01에는 만료하지만, 07:59:50에 다시 빈 결과를 캐시하면 08:04:50까지 남을 수 있다.
이 지연은 재현했지만, 사건 당시 중간 조회 내역은 없어 실제 발생했다고 단정하지 않는다.

## 세 번째 화면: 키움 인증 장애

읽기 전용으로 확인한 운영 tmux의 잔존 출력에서 다음을 확인했다.

```text
계좌 잔고 조회 실패: 인증에 실패했습니다[8005:Token이 유효하지 않습니다]
[046970] 분봉 API 오류: 인증에 실패했습니다[8005:Token이 유효하지 않습니다]
[005930] 분봉 API 오류: 인증에 실패했습니다[8005:Token이 유효하지 않습니다]
WS 로그인 실패: 토큰 인증에 실패했습니다. 접속을 종료합니다 [CODE=8005, MESSAGE=Token이 유효하지 않습니다]
```

확인한 출력 범위에서 잔고 오류 14건, 각 종목 분봉 오류 4건씩, WS 인증 오류
1,781건이 있었다. 전체 장애 기간의 집계가 아니며, 터미널 출력에는 발생 시각과
계좌 식별자가 없어 각각을 08:06에 직접 귀속할 수는 없다.

`backend/logs/events.log:300`의 운영 PID 1103287 시작 시각은 9월 8일 22:40:08이다.
같은 PID가 `:379`에 9월 10일 08:06:17, `:383`에 08:06:42의 046970 추가를 기록했다.
약 33시간 26분 실행된 프로세스이며, 9월 9일 장중 정상 체결 기록도 존재한다.

복구되지 않는 이유:

- `kiwoom.py:65`: 생성자에서 `self.token`을 한 번 발급한다.
- `kiwoom_api.py:149`: 응답의 `expires_dt`는 로그에만 쓰고 토큰 문자열만 반환한다.
  [키움 공식 명세](https://openapi.kiwoom.com/guide/apiguide)에도 만료일 필드가 있다.
- 만료 검사, 선제 갱신, 인증 실패 시 재발급 경로가 없다.
- REST 공통 함수는 연결 오류·HTTP 429를 재시도하지만 인증 오류를 복구하지 않는다.
- `kiwoom.py:283`: WS 재접속에서도 같은 토큰으로 로그인하므로 실패가 반복된다.

화면의 세 증상도 이 흐름으로 설명된다.

- 종목명이 `우리로` 대신 `046970`: 시세 조회 실패가 `None`으로 처리되고 이름이 코드로 대체된다.
- 현재가·고가·저가가 `-`: 초기 시세가 없고 실시간 연결도 인증되지 않는다.
- 잔고 경고: `fetch_positions()` 예외를 `Hub.status_of()`가 잡아
  `position_verified=False`를 내보내면 `StockPanel.jsx:52`에서 경고를 표시한다.
  이는 보유량이 0이라는 판정이 아니다.

상단 녹색 점은 `store.jsx:74`의 **브라우저 ↔ Bach 서버** WS 연결 상태다.
키움 연결 상태를 나타내지 않는다. `실시간 자동` 역시 시계의 자동 장 판정 모드를 뜻한다.
따라서 녹색 점·장전 표시는 키움 인증 장애와 동시에 나타날 수 있다.

## 검증과 수정 우선순위

외부 호출을 대체한 재현에서 다음을 확인했다.

- 빈 일별 응답이 첫 화면 문구를 발생시키고, 11분 후 게시된 응답은 과거 종가 결과가 된다.
- 08:00 직전의 빈 캐시가 게시 후에도 최대 약 5분 동안 남는다.
- 무효 토큰 응답이 이름·현재가 누락과 잔고 미검증을 함께 만들며, 반복 호출에도 재발급하지 않는다.

관련 기존 회귀 테스트 44개도 통과했다(`test_screener`, `test_screener_routing`,
`test_kiwoom_upper_limits`, `test_hub_restore`). 합성 계좌만 활성화하고 `.env` 로딩을
비활성화한 실행에서 검증했다. 기존 FastAPI 시작 이벤트 폐기 예정 경고 2건이 있었다.
재현과 회귀 테스트는 코드 경로를 검증하며, 당시 외부 API 원문 전체를 복원하는 것은 아니다.

수정은 다음 순서가 적절하다.

1. 계좌별 토큰 만료일 보관·선제 갱신·동시 갱신 병합, 인증 실패 시 제한된 재발급,
   갱신된 토큰으로 WS 재로그인과 시세·잔고 재동기화.
2. KRX 미게시를 휴장/장애와 구분하고 제공 예정 시각을 안내. 게시 경계에서 빈 캐시 재조회.
3. 화면에서 앱 연결과 증권사 인증·시세 수신 상태를 구분.
4. 시각·계좌·API 식별자·오류코드·토큰 만료일을 민감값 없이 지속 로그로 보존.

주문에는 조회용 재시도 정책을 그대로 적용하면 안 된다. 주문 결과가 불명확한 경우
접수 여부를 먼저 확인해야 하며, 무조건 재전송하는 토큰 복구는 중복 주문을 만들 수 있다.

## 후속 수정 및 검증

사용자 승인 후 계좌별 토큰 만료 관리·선제 갱신·동시 발급 병합과 조회 인증 복구를 구현했다.
WS는 갱신 토큰으로 재로그인하고 잔고·초기 시세를 재동기화한다.
KRX 게시 대기 응답과 오전 8시 캐시 만료, 계좌별 인증·조회·시세 상태 표시도 추가했다.
전송 계층의 주문 재시도는 제거했다. 전략 자체의 다음 틱 실패 처리는 기존 동작을 유지한다.

최종 검증: 백엔드 170개 테스트 통과, 프런트엔드 프로덕션 빌드 성공,
합성 계좌 매매 데모와 390px 모바일 인증 실패→복구·게시 대기→성공 검증 통과.
운영 이벤트 로그에서도 실전 계좌의 인증 갱신 성공을 확인했다.
실계좌 주문으로 시험하지는 않았다.

운영 서버는 소스 변경을 감지해 자동 재시작된다. 2026-09-11 08:48 KST의 재시작으로
217820·248170은 기존 MONITOR에서 MANUAL_TRADING으로 복원됐다.
기존 복원 규칙대로 감시를 자동 재개하지 않으므로 사용자에게 재설정 필요를 안내했다.
